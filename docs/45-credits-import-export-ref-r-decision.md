# 41.8.5 Credits Import/Export and public Ref R decision lock

## Status and authority

This is the authoritative 41.8.5A decision and code map. This batch is
documentation-only: it changes no production code, schema, migration,
dependency, test, contract version, or translation key. The completed 41.8.4
workflow remains the base contract:

**Choose File → Preview → Apply Import → Confirm → Finished**

## Goals and non-goals

Credits will become an official Import/Export section with a durable public R
identity, separate XLSX/CSV transport, Auto/Add/Update/Delete parity,
warning-based fallbacks, atomic Apply, and backward-compatible migration and
Restore. This lock does not implement the migration, spreadsheet CRUD, schema,
contract-version change, UI redesign, or Batch 41.9.

## Public Ref R contract

Every migrated Credit becomes one first-class record with one permanent Ref.
Reserved section code: **R**.

* display: `RYYMM-NNNN` (for example `R2607-0001`);
* canonical storage: `RYYMMNNNN` (for example `R26070001`);
* allocation uses durable section/month counters and the allocation ledger;
* deleted Refs remain historical and are never reused;
* formatted, canonical, and explicitly supported legacy aliases resolve only in
  section R; display names and row order are never identity.

Technical `credits.id`, `legacySourceKey`, migration keys, aliases, and ledger
ids are internal-only. They are never shown in the application, forms, Preview,
search, or exports. Internal alias resolution may support migration and legacy
file compatibility, but the only user-facing Credit identity is the R Ref.

The TypeScript vocabulary in `src/lib/sakuravaRef.ts` already admits `R`, but
its legacy-prefix resolver and current Rust identity schema/indexes cover only
V/I/P/C/G. 41.8.5B must add R resolution, unique identity storage, aliases,
counters, ledger checks, and Rust validation together.

### Existing-row allocation

Every existing row is preserved, including logical duplicates. Migration orders
the technical `credits.id` values by canonical lexical order, independent of
query or UI row order. For each row, the allocation month is the valid month
from `createdAt`; if `createdAt` is missing or malformed, the migration month
supplied by the migration command is used. Each row receives the next R value
for that month plus a ledger entry, high-water update, and internal alias
mapping. No tuple, display name, or array index participates in identity.

## Actions, relationships, and warnings

Auto/blank plus empty Ref infers Add; an existing R Ref with changed data
infers Update; unchanged data produces no operation; unknown R Ref produces a
Warning/no operation. Delete is never inferred from a missing row and must be
explicit. Explicit Add always allocates a new R Ref and ignores an entered Ref
with a Warning. If Add matches an existing logical tuple, it still creates a
new Credit and new R Ref with a non-blocking duplicate Warning; it never becomes
Update and never merges. Explicit Update/Delete require an existing section-R
Ref.
Unsupported Action affects only its row and is a Warning, not a file blocker.

Invalid nullable relationship values are cleared/left empty with a Warning.
Invalid required relationships omit only that Add row; Update preserves the
existing valid relationship. Credit Delete removes only that Credit and never
deletes a referenced catalog record. Existing automatic cleanup clears nullable
relationships or omits an unsafe catalog Delete while preserving Credits.
Warning count is affected rows, not messages, and warnings never disable Apply.

## Migration design — 41.8.5B

B introduces one transactional migration after the existing Sakurava Ref
migration. Preflight checks SQLite integrity, required columns, unique
technical ids, valid work/Performer/category references, and deterministic
legacy identity. With the automatic safety backup created and verified first,
one transaction must:

1. add R identity storage and its unique index;
2. add/update R counters, aliases, and allocation ledger;
3. allocate Refs deterministically without reuse;
4. write technical/legacy compatibility aliases;
5. validate every Credit and all catalog relationships; and
6. commit only after the authoritative validator passes.

Any failure rolls back and leaves the current database usable. After commit,
the connection, migration state, counters, aliases, and catalog are reloaded
and validated again. Empty and Credits-only catalogs are valid when metadata
and identity ledgers are valid. Malformed relationships are reported, not
silently redirected. Duplicate legacy rows follow the ambiguity rule above.

## Alias, ledger, counter, and Restore compatibility

R participates in `sakuravaRefCounters`, `sakuravaRefAliases`, and durable
high-water state. Restoring an older package without R columns stages it,
validates it, runs the same migration, and activates it only after validation.
A newer package must not downgrade a migrated database. Counters reconcile to
the maximum observed allocation and never reset from row counts.

The package contract version need not increase solely for this backward-
compatible database extension. B must prove that absence of R columns is a
migratable legacy condition, unknown manifest fields remain safe, and newer
packages cannot bypass validation. No contract-version change is authorized in
41.8.5A.

## 41.8.5B implementation note

Implemented migration identifier: `41.8.5B-credit-ref-r-v1`. The `credits`
table now stores canonical `sakuravaRef` alongside its hidden technical `id`,
with `idx_credits_sakurava_ref` and the existing R section counter, alias, and
schema-migration ledger infrastructure. The existing `sakuravaRefCounters` and
`sakuravaRefAliases` tables remain the sole durable high-water and alias store.

Legacy Credit rows migrate in one transaction. `createdAt` accepts the current
millisecond timestamp representation and valid ISO `YYYY-MM` prefix; missing or
malformed timestamps use the one supplied migration month. Rows are ordered by
binary canonical `credits.id` within each month. Logical duplicates remain
separate. Existing valid R values are preserved, while invalid values or
conflicting unique mappings reject the migration. New Credit creation allocates
an R Ref atomically and normal updates preserve it; Credit deletion leaves the
counter/ledger history intact.

Staged Restore reuses the deterministic Credit migration before activation when
the base identity upgrade is already present but the Credit migration marker is
absent. Older packages with no Credit Ref therefore remain migratable; newer
packages retain valid R values and reconcile counters. The package contract
version remains unchanged. Final schema, counter, alias, catalog-relationship,
and migration-state validation still runs before transaction commit/activation.

Automated coverage includes legacy duplicate preservation, malformed/missing
timestamp fallback, R allocation and update immutability, backup Preview
compatibility, full Rust suite, and production TypeScript build. Manual
disposable migration/CRUD/Restore smoke remains required before 41.8.5B
closure. 41.8.5C remains limited to Credits XLSX/CSV Import/Export; Batch 41.9
is unchanged.
