# 41.8.5 Credits Import/Export and public Ref R decision lock

## Status and authority

This is the authoritative 41.8.5A decision and code map. This batch is
documentation-only: it changes no production code, schema, migration,
dependency, test, contract version, or translation key. The completed 41.8.4
workflow remains the base contract:

**Choose File → Preview → Apply Import → Confirm → Finished**

Preview is read-only, with filters All, Add, Update, Delete, Warning and
columns Row, Section, Sakurava Ref, Record, Action, Details. Review, Attention,
Resolution, Import Ref, and Import Resolution remain excluded.

## Goals and non-goals

Credits will become an official Import/Export section with a durable public R
identity, separate XLSX/CSV transport, Auto/Add/Update/Delete parity,
warning-based fallbacks, atomic Apply, and backward-compatible migration and
Restore. This lock does not implement the migration, spreadsheet CRUD, schema,
contract-version change, UI redesign, or Batch 41.9.

## Current Credits architecture

`src-tauri/src/database.rs` defines `CREATE_CREDITS_TABLE_SQL` and the
`credits` table:

| Column | Current meaning |
|---|---|
| `id` | Technical primary key generated by `new_id("credit")`; not public identity. |
| `workType`, `workId` | Required target section (`video`/`image`) and technical target id. |
| `performerId` | Required technical Performer id. |
| `characterName` | Required text column, default empty string. |
| `characterOriginalName`, `creditedAs` | Nullable display text. |
| `creditedAsMode` | Required `auto`/`custom`, default `auto`. |
| `creditTypeCategoryId`, `roleImportanceCategoryId` | Nullable Managed Category keys. |
| `characterMode` | Required `text`/`self`/`linked`, default `text`. |
| `characterId` | Nullable technical identity; no current resolver. |
| `billingOrder` | Nullable integer display/order. |

There are no declared foreign keys. `validate_catalog_integrity` and
`validate_credit_references` enforce work, Performer, and Category targets.
Each Credit has one work target and one Performer and may have two optional
Category targets. There is no current Glossary relationship or Credit-owned
catalog record.

Rust types and commands are `Credit`, `CreditInput`, `CreditPatch`,
`credit_create`, `credit_list`, `credit_get`, `credit_update`, `credit_delete`,
`credit_list_by_work`, and `credit_list_by_performer` in
`src-tauri/src/commands.rs`. TypeScript mirrors them in
`src/backend/types.ts` and `src/runtime/creditCommands.ts`.
`src/lib/workCredits.ts` reconciles form lists; `CreditEditor.tsx`, the Video
and Image form/detail pages, Performer detail, and category management consume
the runtime API. `SettingsPage.tsx` already loads Credits into the import
context. Existing tests include Rust Credit CRUD/integrity tests,
`src/lib/workCredits.test.ts`, runtime command tests, and App/detail tests.

`backfill_legacy_credits` creates rows from Video/Image `relatedPerformersJson`.
Its current `legacySourceKey` and technical id include work, performer, and
array index. The migration source identity is nevertheless the existing
`credits.id`, never the array position or a logical tuple. The existing id is
stable for the migration and remains the hidden internal identity.

Backups already contain Credits because the package copies the complete SQLite
database. Package Preview counts the `credits` table, validates the required
table, and Restore runs the same staged identity/catalog checks. The current
directory package contains `manifest.json` and `database.sqlite`; there is no
separate Credits artifact today.

## Public Ref R contract

Every migrated Credit becomes one first-class record with one permanent Ref.
Reserved section code: **R**.

* display: `RYYMM-NNNN` (for example `R2607-0001`);
* canonical storage: `RYYMMNNNN` (for example `R26070001`);
* allocation uses durable section/month counters and the allocation ledger;
* deleted Refs remain historical and are never reused;
* formatted, canonical, and explicitly supported legacy aliases resolve only in
  section R; display names and row order are never identity.

Technical `credits.id`, `legacySourceKey`, migration keys, aliases, and ledger
ids are internal-only. They are never shown in the application, forms, Preview,
search, or exports. Internal alias resolution may support migration and legacy
file compatibility, but the only user-facing Credit identity is the R Ref.

The TypeScript vocabulary in `src/lib/sakuravaRef.ts` already admits `R`, but
its legacy-prefix resolver and current Rust identity schema/indexes cover only
V/I/P/C/G. 41.8.5B must add R resolution, unique identity storage, aliases,
counters, ledger checks, and Rust validation together.

### Existing-row allocation

Every existing row is preserved, including logical duplicates. Migration orders
the technical `credits.id` values by canonical lexical order, independent of
query or UI row order. For each row, the allocation month is the valid month
from `createdAt`; if `createdAt` is missing or malformed, the migration month
supplied by the migration command is used. Each row receives the next R value
for that month plus a ledger entry, high-water update, and internal alias
mapping. No tuple, display name, or array index participates in identity.

## Spreadsheet contract

Credits are separate from all catalog sheets. XLSX adds a `Credits` sheet;
CSV adds `credits.csv`. Neither includes Import Ref or Import Resolution.

System columns are exactly `Action` and `Sakurava Ref`. Public Actions are
Auto, Add, Update, Delete; blank Action is Auto.

| Header | Field/type | Required | Add/default and Warning | Clear | Relation |
|---|---|---:|---|---|---|
| Work Type | `workType`, Video/Image enum | yes | missing/invalid: row not applied | no | Videos or Images |
| Work Ref | `workId`, Ref | yes | missing/wrong section: row not applied | no | required work target |
| Performer Ref | `performerId`, Ref | yes | missing/wrong section: row not applied | no | required Performer |
| Character / Role | `characterName`, text | yes | empty uses `N/A` | no | none |
| Original Character | `characterOriginalName`, text | no | empty | yes | none |
| Credited As Mode | `creditedAsMode`, Auto/Custom | yes | official default Auto | no | none |
| Credited As | `creditedAs`, text | no | empty when Auto | yes | none |
| Credit Type | `creditTypeCategoryId`, Category Ref | no | invalid becomes empty + Warning | yes | Managed Category |
| Role Importance | `roleImportanceCategoryId`, Category Ref | no | invalid becomes empty + Warning | yes | Managed Category |
| Character Mode | `characterMode`, Text/Self | yes | official default Text | no | none |
| Billing Order | `billingOrder`, integer | no | invalid becomes empty + Warning | yes | none |
| Note | `note`, text | no | empty | yes | none |

The final exact headers are: `Action`, `Sakurava Ref`, `Work Type`, `Work Ref`,
`Performer Ref`, `Character / Role`, `Original Character`, `Credited As Mode`,
`Credited As`, `Credit Type`, `Role Importance`, `Character Mode`, `Billing
Order`, and `Note`. These map only to fields currently persisted and editable
by `CreditEditor` and the existing form reconciliation. There is no Character
Ref header and no new relationship mode. 41.8.5C may accept documented legacy
header aliases, but never technical ids, migration keys, aliases, or names as
identity. `[[SAKURAVA:CLEAR:v1]]` is accepted only for nullable fields. Delete
validates only Action, Credit Ref, section, target existence, and dependency
behavior; unused cells are ignored.

`characterId` is retained as an existing nullable database field for backward
compatibility, but Character Ref import/export is excluded. `characterMode`
supports only the already editable Text/Self behavior in this batch. Linked
mode expansion and any Character relationship type are separate future work,
not 41.8.5B, C, or D.

## Actions, relationships, and warnings

Auto/blank plus empty Ref infers Add; an existing R Ref with changed data
infers Update; unchanged data produces no operation; unknown R Ref produces a
Warning/no operation. Delete is never inferred from a missing row and must be
explicit. Explicit Add always allocates a new R Ref and ignores an entered Ref
with a Warning. If Add matches an existing logical tuple, it still creates a
new Credit and new R Ref with a non-blocking duplicate Warning; it never becomes
Update and never merges. Explicit Update/Delete require an existing section-R
Ref.
Unsupported Action affects only its row and is a Warning, not a file blocker.

Invalid nullable relationship values are cleared/left empty with a Warning.
Invalid required relationships omit only that Add row; Update preserves the
existing valid relationship. Credit Delete removes only that Credit and never
deletes a referenced catalog record. Existing automatic cleanup clears nullable
relationships or omits an unsafe catalog Delete while preserving Credits.
Warning count is affected rows, not messages, and warnings never disable Apply.

## Migration design — 41.8.5B

B introduces one transactional migration after the existing Sakurava Ref
migration. Preflight checks SQLite integrity, required columns, unique
technical ids, valid work/Performer/category references, and deterministic
legacy identity. With the automatic safety backup created and verified first,
one transaction must:

1. add R identity storage and its unique index;
2. add/update R counters, aliases, and allocation ledger;
3. allocate Refs deterministically without reuse;
4. write technical/legacy compatibility aliases;
5. validate every Credit and all catalog relationships; and
6. commit only after the authoritative validator passes.

Any failure rolls back and leaves the current database usable. After commit,
the connection, migration state, counters, aliases, and catalog are reloaded
and validated again. Empty and Credits-only catalogs are valid when metadata
and identity ledgers are valid. Malformed relationships are reported, not
silently redirected. Duplicate legacy rows follow the ambiguity rule above.

## Alias, ledger, counter, and Restore compatibility

R participates in `sakuravaRefCounters`, `sakuravaRefAliases`, and durable
high-water state. Restoring an older package without R columns stages it,
validates it, runs the same migration, and activates it only after validation.
A newer package must not downgrade a migrated database. Counters reconcile to
the maximum observed allocation and never reset from row counts.

The package contract version need not increase solely for this backward-
compatible database extension. B must prove that absence of R columns is a
migratable legacy condition, unknown manifest fields remain safe, and newer
packages cannot bypass validation. No contract-version change is authorized in
41.8.5A.

existing relationship storage and UI.

**Defer:** migration implementation (B), spreadsheet CRUD (C), closure and
manual verification (D), translation-management changes, unrelated settings,
and Batch 41.9.

## Tests, risks, and implementation verification items

B acceptance requires deterministic `credits.id`-ordered allocation, timestamp
month fallback, preservation of logical duplicates, R canonical/formatted/alias
resolution, non-reuse/high-water continuity, empty/Credits-only migration,
rollback, old/new package Restore, counter/alias validation, final migration
state validation, reopen, and restart tests.

C acceptance requires exact Credits sheet and `credits.csv` headers; every
field fallback and Clear rule; Auto/Add/Update/Delete; wrong-section/unknown
Refs; Delete payload bypass; relationship cleanup; matching Warning/confirmation
counts; canonical TypeScript/Rust payload parity; atomic rollback; and proof
that Credit Delete never deletes catalog targets.

D acceptance requires export-edit-import, Credit Delete, old/new Restore,
restart/recovery, non-reuse, disposable desktop smoke, documentation, and
commit-readiness tests.

The product decisions are closed. B still has implementation verification
items, not open product choices: confirm the concrete migration identifier and
SQL column/index names against the existing migration registry; prove the
`createdAt` parser and migration-month fallback; prove that old package
validation routes through staged migration; and add the required Rust/TypeScript
tests. These checks must not change the decisions above.

## 41.8.5 boundaries and exclusion

* **41.8.5A:** this decision lock and map only; no production changes.
* **41.8.5B:** deterministic `credits.id` → R migration using `createdAt` month
  with migration-month fallback; duplicate preservation; ledger, alias, counter,
  high-water, non-reuse, staged Restore migration, rollback, and final
  migration-state validation. No spreadsheet CRUD.
* **41.8.5C:** a separate `Credits` XLSX sheet and `credits.csv` using only the
  exact headers above, Action/Sakurava Ref system columns, Auto/Add/Update/Delete,
  duplicate-Add Warning, Preview/Warning, plan/Apply/export tests, and atomic
  runtime integration. No Review/resolution workflow.
* **41.8.5D:** all existing Credits migrated without merging, stable R Refs
  after restart, export/edit/import round trip, non-blocking duplicate Add,
  R-targeted Update/Delete, older/newer Restore, high-water continuity, and
  no recovery state.

Batch 41.9 is explicitly excluded and remains unchanged.
